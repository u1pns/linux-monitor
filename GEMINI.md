# Server Monitoring and Maintenance System

## 1. Core Philosophy

This project is an unattended server monitoring and maintenance system designed to be robust, lightweight, and silent unless action is needed. The core principles are:

1.  **Report on Change:** The system is stateful. It only sends alerts for *new* or *changed* conditions to prevent alert fatigue. A persistent problem will only be reported once.
2.  **Automated Maintenance:** It performs routine cleaning tasks (like log truncation) automatically to prevent common server issues like running out of disk space.
3.  **Self-Awareness:** It includes a "heartbeat" mechanism. If you don't receive any alerts for 15 days, it will send a positive confirmation ("All Clear") to assure you that the system itself is still running correctly.
4.  **Extensibility:** Adding new checks or cleaning tasks is as simple as adding a new file to the appropriate directory.

---

## 2. How it Works: The Orchestration Flow

The entire system is controlled by a single entry point, `run_daily.js`, which is executed once a day at 8 AM via a cron job.

When `run_daily.js` runs, it performs the following sequence:

1.  **Run Alerts (Always):** It **always** executes the `alerts.js` script to check the server's status.
2.  **Check the Day:** It checks if the current day is Sunday.
3.  **Run Cleaners (Sundays Only):** If it is Sunday, it then executes the `cleaners.js` script to perform weekly maintenance tasks.

This ensures that monitoring happens every day, while more resource-intensive cleaning tasks are reserved for the weekend.

---

## 3. The Alerting System (`alerts.js`)

`alerts.js` is responsible for monitoring the server's health.

-   **Execution:** It runs all `.js` files located in the `monitors/` directory.
-   **Alert Collection:** Each monitor script checks a specific aspect of the system. If it finds a new issue, it writes a Markdown-formatted alert to a temporary file (`monitors/alerts.txt`).
-   **Error Reporting:** If a monitor script itself fails to execute (due to a syntax error or any other crash), `alerts.js` will catch this failure, generate a special alert for it, and include it in the email.
-   **Emailing:** If `monitors/alerts.txt` contains any content after all monitors have run, the content is converted to an HTML email and sent.
-   **Logging:** The entire process, including the number of alerts generated by each monitor, is logged to `alerts.log`.

### The Heartbeat Mechanism

To ensure the system is silently working, `alerts.js` manages a status file: `monitors/laststatus/last_email_sent.status`.

-   Each time an email is successfully sent (either an alert or a heartbeat), the current timestamp is written to this file.
-   If `alerts.js` runs and finds **no new alerts**, it checks this timestamp.
-   If more than **15 days** have passed since the last email, it sends a special "System Status: All Clear" email and updates the timestamp. This confirms the system is still alive and well.

---

## 4. The Maintenance System (`cleaners.js`)

`cleaners.js` is responsible for performing routine maintenance.

-   **Execution:** It runs all `.js` files located in the `cleaners/` directory.
-   **Purpose:** These scripts are not for monitoring. They perform active tasks like truncating large log files, vacuuming databases, or clearing temporary directories.
-   **Logging:** All operations are logged to `cleaners.log`.

---

## 5. How to Extend the System

### Adding a New Monitor

1.  Create a new JavaScript file (e.g., `my_new_check.js`) inside the `monitors/` directory.
2.  The script **must** adhere to three rules:
    1.  **Be Stateful:** It must save its last reported state (e.g., in a file within `monitors/laststatus/`). It should only generate an alert if the current state is different from the last saved state.
    2.  **Use Markdown:** Any alert written to `monitors/alerts.txt` must be in Markdown format, starting with a level-two heading (`## My New Check`).
    3.  **Output Alert Count:** The script's final action must be to print the number of new alerts it generated to standard output (e.g., `console.log(1)` or `console.log(0)`). This is crucial for logging.
3.  No further configuration is needed. `alerts.js` will automatically pick it up on its next run.

### Adding a New Cleaner

1.  Create a new JavaScript file (e.g., `cleanup_temp_files.js`) inside the `cleaners/` directory.
2.  Write the Node.js code to perform the desired maintenance task. It's recommended to log actions to the console (`console.log`) so they are captured in `cleaners.log`.
3.  No further configuration is needed. `cleaners.js` will automatically run it on the next scheduled Sunday.

## 6. Project Structure

-   `run_daily.js`: The main orchestrator script executed by cron.
-   `setup_cron.sh`: An idempotent script to configure the cron job for `run_daily.js`.
-   `alerts.js`: Orchestrates all monitor scripts.
-   `alerts.log`: Log file for the alerting system.
-   `cleaners.js`: Orchestrates all cleaner scripts.
-   `cleaners.log`: Log file for the maintenance system.
-   `monitors/`: Directory for all monitoring scripts.
    -   `disk_space.js`, `cpu_load.js`, etc.
    -   `alerts.txt`: Temporary file for collecting alerts during a run.
    -   `laststatus/`: Directory for state files.
        -   `disk_space.status`, `ip_blocks.status`, etc.
        -   `last_email_sent.status`: Timestamp for the heartbeat mechanism.
-   `cleaners/`: Directory for all maintenance scripts.
    -   `journal_vacuum.js`, `clean_telemetry_log.js`, etc.

## 7. Development Environment & Portability

This system was developed and tested on a specific server environment. While the core logic is portable, many of the monitor scripts are tailored to the services and log paths of this environment.

### 7.1. Server Configuration

-   **Operating System**: Ubuntu
-   **Key Services**:
    -   **PM2**: Used for managing Node.js applications. The `pm2_status.js` and `pm2_errors.js` monitors depend on its presence and log paths (`/root/.pm2/logs/`).
    -   **Nginx**: Used as a web server. The `nginx_errors.js` monitor queries its logs via `journalctl`.
    -   **Fail2Ban**: Used for blocking malicious IPs. The `ip_blocks.js` monitor depends on its log file (`/var/log/fail2ban.log`).
    -   **Systemd/Journald**: The primary logging system. Many monitors (`intrusion_attempts.js`, `nginx_errors.js`, `sudo_activity.js`, `system_log_errors.js`) rely on `journalctl` to query logs.

### 7.2. Adapting to Other Systems

When deploying this project on a different server, it is crucial to review the scripts in the `monitors/` and `cleaners/` directories:

-   **Check Service Dependencies**: If a service like PM2 or Nginx is not installed, the corresponding monitor will fail or produce no output. These monitor files should be **deleted** or adapted.
-   **Verify Log Paths**: Some scripts contain hardcoded paths to log files (e.g., `/var/log/fail2ban.log`). If your system stores logs in a different location, you must update the paths in the relevant scripts.
-   **Review Commands**: The scripts use standard Linux commands (`df`, `vmstat`, `journalctl`). If your OS uses different commands or flags, the scripts will need to be adjusted.
-   **Add or Remove Scripts**: The modular nature of this project makes it easy to add new monitors for services on your specific server or remove those that are not applicable.

## 8. Protocolo de Diagnóstico

When a problem is reported, follow these steps systematically:

1.  **Check the Logs:** Inspect `alerts.log` and `cleaners.log` first. They record the execution flow, the output of each script, and any errors.
2.  **Consult This Document:** Reread the "Orchestration Flow" and "Development Environment" sections in this file to understand how the components interact and what their dependencies are.
3.  **Form a Hypothesis:** Based on the flow, identify the likely source. (e.g., "No emails are being sent" -> check `alerts.log` for errors or heartbeat status. "A log file is too big" -> check `cleaners.log` to see if the relevant cleaner ran).
4.  **Investigate the Source:** Use tools (`read_file`, `ls`) to inspect the files involved (`alerts.txt`, a specific monitor, a `.status` file, etc.).
5.  **Ask the User as a Last Resort:** Only ask for information if it's impossible to diagnose from the project files (e.g., to confirm the external reception of an email).
